# Document History: compact list research

Researched 7 October 2026 for the existing Django Telegram Portal. This is a bounded presentation recommendation, not a new workflow contract or cross-app component mandate. Proposed layout values below are design judgments; source requirements are identified separately.

1. **Use a single aligned list.** Present documents as full-width rows separated by a light rule, rather than repeated elevated cards. Keep the same content order in each row: document reference, concise metadata, status, actions. Carbon recommends contained lists for related content in small spaces and inline actions; Fluent recommends parallel row structures for scanning. [Carbon contained list](https://www.carbondesignsystem.com/building-blocks/core/components/contained-list/guidelines), [Fluent list](https://fluent2.microsoft.design/components/web/react/core/list/usage)

2. **Give identity first emphasis.** Keep `Order HB…` or `Payment #…` as the strongest line. Put partner/order, case count, version and date in smaller secondary text. Keep actionable failure and unsigned/review states visible. This hierarchy is an application of Carbon's concise, consistent row-content guidance; it is not a prescribed font scale. [Carbon contained list](https://www.carbondesignsystem.com/building-blocks/core/components/contained-list/guidelines)

3. **Keep compact actions beside their document.** Use one consistent action order for preview, download and signed evidence; put uncommon replacement actions in a clearly labelled overflow/disclosure. Avoid repeating the main action in the secondary menu. Keep controls available to touch and keyboard users instead of depending on hover. [Carbon contained list](https://www.carbondesignsystem.com/building-blocks/core/components/contained-list/guidelines), [Fluent button](https://fluent2.microsoft.design/components/web/react/core/button/usage)

4. **Restrain decoration.** Prefer the existing icon family, consistent 16–20 px icons, neutral monochrome color and center alignment beside text. Treat any file icon as decorative when text already names the type; retain clear accessible names for icon buttons. Reserve strong colors for meaningful state. [Carbon icons](https://www.carbondesignsystem.com/building-blocks/foundations/icons/guidelines), [Carbon contained list](https://www.carbondesignsystem.com/building-blocks/core/components/contained-list/guidelines)

5. **Reduce empty space, retain touch space.** Start with roughly 12 px row padding and 4–6 px internal gaps; let metadata and actions wrap at 320 px instead of shrinking text or forcing horizontal scrolling. Keep interactive targets at least 44 × 44 CSS px as a mobile design target. WCAG 2.2 AA's minimum is 24 × 24 CSS px with defined exceptions; 44 × 44 is its enhanced criterion and Carbon's icon guidance. [Carbon icons](https://www.carbondesignsystem.com/building-blocks/foundations/icons/guidelines), [WCAG minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum), [WCAG enhanced](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced)

6. **Disclose rare details.** Keep generated-by attribution, earlier workbook versions and earlier signed scans under `Details` or `Earlier versions`. Keep the current signature/review/storage state and the next required action visible. GOV.UK recommends details for information needed only by some users, and warns against hiding what most users need. Preserve existing permission and exact-version rules. [GOV.UK details](https://design-system.service.gov.uk/components/details/)

7. **Make valid phone numbers explicit links.** Where contact numbers appear, render an ordinary anchor whose visible number stays readable and whose `href` uses a validated global number, such as `tel:+254…`, without spaces. RFC 3966 recommends global form in HTML links and forbids spaces in the URI. Apple documents iOS handing `tel:` to Phone and asking for confirmation; behavior remains device/handler dependent, so verify in Telegram on supported phones. Invalid/missing numbers remain plain text. [RFC 3966, sections 5.1.1 and 8](https://www.rfc-editor.org/rfc/rfc3966.html), [Apple phone links](https://developer.apple.com/library/archive/featuredarticles/iPhoneURLScheme_Reference/PhoneLinks/PhoneLinks.html)

Implementation boundary: change presentation and link markup only. Preserve IDs, current event hooks, authorized actions, version finality, upload attestation and existing document-preview behavior. Verify synthetic long references, narrow widths, light/dark themes, keyboard focus and expanded history; browser automation cannot prove an actual phone call launches.

Implementation choices: use 8 px row padding and keep replacement as a direct,
labelled icon alongside the signed-copy actions. The user's existing preference
for direct actions takes precedence over an additional overflow menu.
