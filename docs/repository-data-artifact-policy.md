# Repository data and artifact policy

## Rule

Git must not contain customer or staff data, operational exports, credentials,
real evidence, generated documents, or screenshots of live workflows. A private
repository is still a replicated disclosure surface: clones, CI logs, caches,
backups, and forks can retain every committed byte.

The default is therefore **do not commit the file**. Store operational evidence
only in the approved Django/Drive workflow and keep local exports outside the
repository.

## Controlled artifacts

CI treats spreadsheets, CSV/TSV data, Office documents, PDFs, archives, private
key formats, and raster images as controlled artifacts. A genuinely public or
fully synthetic artifact may be committed only when all of these are true:

1. Its contents and metadata have been reviewed for customer data, staff data,
   credentials, access links, and reusable identifiers.
2. A synthetic fixture contains invented values and cannot be mistaken for a
   real operational record.
3. The exact repository path, SHA-256, classification, and purpose are recorded
   in `scripts/tracked_artifact_allowlist.json`.
4. The file is force-added only after the allowlist review; `.gitignore` blocks
   these file types by default.

Sanitized binary test fixtures must live under
`core/test_fixtures/sanitized/`. Reviewed public brand assets must live under
`core/static/`. The scanner validates the classification-to-path relationship;
an allowlist entry cannot approve an operational export in an arbitrary path.

Changing an allowlisted file changes its hash and intentionally fails CI until
the new bytes receive a fresh review. Path-based trust alone is not sufficient.
Controlled formats are also marked as binary in `.gitattributes`, preventing a
deletion or hash change from copying their contents into a pull-request diff.

## Local audit

Run:

```bash
python scripts/audit_tracked_artifacts.py
python -m unittest scripts.tests.test_audit_tracked_artifacts
```

The scanner reports only the affected path and finding category. It never
prints a matched token or customer value.

## Historical exposure response

Removing a file in a new commit does not remove it from Git history. If a
review finds real customer/staff data or a credential in history:

1. Stop distributing new clones and record affected paths privately.
2. Rotate credentials and reusable access links immediately where applicable.
3. Obtain explicit repository-owner approval for a coordinated history rewrite.
4. Rewrite and force-update the remote, then require fresh clones.
5. Re-run the artifact scanner and retain private incident evidence outside Git.

History rewriting is deliberately not an ordinary cleanup command: it disrupts
every clone and must be coordinated separately.

## 2026-08-31 current-tree audit

The initial audit classified 39 tracked data/media artifacts without copying
their contents into this document:

- 27 root screenshots contained operational UI captures, including visible
  personal, financial, workflow, or access-link information; removed.
- 5 root Excel workbooks contained operational/template data and identifier-like
  values; removed. Reproducible templates remain generated by repository scripts.
- 1 root DOCX operational policy file contained identifier-like values; removed.
- 3 generated Jawabu preview CSVs were removed; the cleaned preview contained
  high-confidence phone-number patterns.
- 1 Office temporary lock file was removed.
- 1 unreferenced duplicate root logo was removed.
- 1 public application logo remains under `core/static/miniapp/` and is
  hash-pinned in the allowlist.

Because the removed files remain in earlier commits, the repository owner must
treat historical cleanup as a separate privacy-response decision.
